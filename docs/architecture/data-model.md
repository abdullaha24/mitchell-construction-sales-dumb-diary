> Status: **v0.9** (2026-11-11). v0.9: `Sites.earlier_contacts` and the `Activity` action `contact`
> (spec 011, ADR-0011: a new main contact person keeps the old one). v0.8: an `Activity` `update` row carries `value_rs` /
> `payment_terms` only when they changed; the kept copy also holds last month, with a `months` part
> (spec 009, owner S9-13). v0.7: `Activity.rep` can be `admin`, region and house targets kept
> (spec 008, ADR-0010). v0.6: `worked_at`, `note_at` and the `snooze` action (spec 007, ADR-0009). v0.5: targets kept with the salesmen list (spec 006). v0.3 came from the owner interview and session 2 answers; v0.4
> aligns the Meta-Data reading notes with [spec 001](../specs/001-foundations.md) as built. The tabs and headers act as the app's database schema. **Any change
> here must be made in the same change as the code.**

Two spreadsheets (ADR-0005):

| Spreadsheet | Owned by | App access |
| --- | --- | --- |
| **Mitchell Sales Meta-Data** | Owner, edited by hand | **Read only** |
| **Sales Diary** | The app | Read and write |

Conventions:
- Row 1 of every tab is the header. Code finds columns **by header name**, never by position.
- IDs are generated by the app and never reused.
- Timestamps are written by the server, never typed by people.
- The salesman ID everywhere is his `Rep` code from `Rep_Mapping` (e.g. `RIA`).

## Sales Diary (app-owned)

### Tab `Links`: private link codes (ADR-0002)

**Created by Check setup from phase 2** ([spec 002](../specs/002-private-links.md)). Rows are only
added or set inactive by the app, never deleted, so the tab is a history of every link.
| Column | Example | Notes |
| --- | --- | --- |
| `role` | rep | `rep` (a salesman) or `owner` (ADR-0006). The owner is shown to people as **Admin** (owner P7-7), but this value stays `owner`: it is his working link's row. |
| `rep` | RIA | For `rep` rows: must exist in `Rep_Mapping`. Blank for the `owner` row. |
| `token` | *(64 letters/digits)* | **Secret.** Stays **visible** in the tab (owner's choice P2-1, risk accepted): anyone who sees the tab can copy a working link. Column formatted as plain text. |
| `active` | TRUE | FALSE = link cancelled. At most one TRUE row per person; **New link** cancels older ones. |
| `issued_at` | | Server timestamp. |

The owner's link lives here too, as a `role` = `owner` row with `rep` blank (ADR-0006). A
salesman's link works only while his `rep` is still in Meta-Data `Rep_Mapping`.

### Tab `Sites`: current state, one row per site
| Column | Example | Notes |
| --- | --- | --- |

| `rep` | RIA | The one salesman who owns it (ADR-0004). The owner edits this to hand sites over when a salesman leaves. `Activity` rows keep the original salesman (history). |
| `region` | North | Copied from `Rep_Mapping` when created. If the owner hands a site to a salesman in another region, he updates this too. |
| `site_name` | F-11 Commercial Tower | |
| `buyer_type` | Contractor / Applicator | Contractor / Applicator, Project Owner, Consultant, Dealer. |
| `area` | DHA | Picked from areas in `Lists` for his region, or a new one he added. |

| `products` | Tile Adhesives \| Tile Grouts | Product **categories** from `Lists`, joined by ` \| ` (names can contain commas). In `Lists` order. |
| `stage` | Rate Quoted | One of the five glossary stages. |

| `payment_terms` | Credit | `Cash` or `Credit`. Required with a value. |
| `lost_reason` | Other | An active `lost_reason` from `Lists`. Required at Lost / Dead; cleared when the site moves to any other stage. |

| `last_note` | Waiting for consultant | The latest quick note (up to 200 letters); kept until a new one is written. Required if the lost reason is Other. A note the admin wrote starts **"Admin: "** (owner P7-4; also in the `Activity` note). |
| `created_at` | | Server timestamp. |
| `updated_at` | | Server timestamp: the last change of any kind (Update, Edit details, Snooze). |
| `worked_at` | | Server timestamp: when the site was added or last saved from the salesman's **Update** screen (spec 007, ADR-0009). **Drives "going cold"** (Sample / Trial or Rate Quoted, 7 days). Not written by Edit details, Snooze (owner P6-2) or the admin's Update (P7-5). Blank (a row typed by hand) → `created_at` is used. |
| `note_at` | | Server timestamp: when `last_note` was written (adding a site or an Update with a note). The day on the card's last-spoken line. Blank → the note shows without a day. |
| `earlier_contacts` | `923331112222 · Asif · 2026-11-11` | The site's **earlier contacts** (spec 011, ADR-0011): plain text, one person per line, **newest first**, `<phone or -> · <name> · <yyyy-MM-dd>` (the day they stopped being main; phone first and date last, so a name with " · " still parses). At most **20** (the oldest drops off; the history keeps it). Written by an Update with + New contact person or Make main, and by Edit details' "Yes, keep the old one"; written as text (`asText_`). The new main contact's number is never also kept here. Blank = none. A salesman's page gets them only for his own sites (ADR-0004); the duplicate check reads them as yes/no. |

### Tab `Activity`: history, append-only
One row per change. **Never edited or deleted by the app.**

| Column | Example | Notes |
| --- | --- | --- |
| `activity_id` | `A0004567` | `A` + 7 digits, one more than the highest in `Activity`. |
| `timestamp` | | Server time. |
| `rep` | RIA | Who made the change: a salesman's code, or **`admin`** for an Update the owner made from his admin screen (spec 008, ADR-0010; the site's salesman is in `Sites.rep`). Admin rows never count as a salesman's work. |
| `site_id` | `S000123` | |
| `action` | stage_change | `created` (new site; since spec 005 with the stage it started at and its value, terms, reason and note), `stage_change` (with `from_stage` / `to_stage`), `update` (same stage: value, note or follow-up; since spec 009 its `value_rs` / `payment_terms` are filled **only when the Rs. or Cash / Credit changed**, so a revised price can be told from a plain note (owner S9-13); rows saved before keep the value either way), `details` (Edit details: `note` lists what changed, with the old → new number), `snooze` (spec 007: the follow-up pushed from the card; `next_followup` = the new date, other detail columns blank; not counted as work), `contact` (spec 011: a new main contact person; `note` = *"New contact: Bilal · 923001234567 (was Asif · 923331112222)"* or *"Main contact again: …"*, other detail columns blank; a save but never work, like `details`). An Update with a new contact and other changes writes its `update` / `stage_change` row and then the `contact` row (ID one more) in one write; a contact-only Update writes only the `contact` row (no `worked_at`, no `note_at`). Edit details' "Yes, keep the old one" writes a `contact` row, plus a `details` row only if other fields changed. |
| `from_stage` | Sample / Trial | Blank if not a stage change. |
| `to_stage` | Rate Quoted | |
| `value_rs` | 450000 | On `created` and `stage_change` rows at Rate Quoted / Won (Order); on an `update` row only when it changed (spec 009). |
| `payment_terms` | Credit | With `value_rs`. |
| `lost_reason` | | If given. |
| `note` | Quoted WP-100 @ Rs. 1,450 | |
| `next_followup` | 2026-11-06 | If changed. |

### Tab `Lists`: pick-list values
So the owner can change buttons without code changes.

| Column | Example | Notes |
| --- | --- | --- |
| `list` | area | `area`, `product_category`, `lost_reason`, `buyer_type`. |
| `value` | DHA | |
| `region` | North | For `area`. Blank = all regions. |
| `added_by` | owner / RIA | Areas added by salesmen show who added them, so the owner can tidy duplicates. |
| `active` | TRUE | |
| `sort` | 10 | Display order. |

Starting contents (filled in by phase 1 setup, only when a list has no rows yet):
- `product_category`: the owner's 11 categories, in this `sort` order: Tile Adhesives, Waterproofing
  Job, Floor Hardeners, Bonding Agents & Sealants, Waterproofing Products, Tile Grouts, Structural
  Grouts, Restoration & Repair Products, Admixtures, Surface Protection, Mortars, Plasters & Putties.
- `lost_reason` and `buyer_type`: the values in the [glossary](../product/glossary.md).
- `area`: **empty.** Salesmen add areas as they go. Salesmen in the same region see each other's
  area **names** (needed so they can pick instead of retype, and for the "Did you mean …?"
  suggestion), but never who added them. That is only an area name, no site or contact data, so
  ADR-0004 still holds.

## Kept by the script (not in a sheet)

| Store | Key | Holds |
| --- | --- | --- |
| Script Properties | `salesmen` | The salesmen list from `Rep_Mapping` (codes and regions only), **each current salesman's `Rep-Targets` amount for last month, this month and next month** (as `RIA\|yyyy-MM`: whole Rs.; next month so the 1st of a month rolls over without a refresh, spec 006; last month for the Last month summary, spec 009), **the `Targets` amounts for North, Center, South and `UNASSIGNED`** for the same three months, in their own `regionTargets` part (spec 008, admin only), **`months`: the three months it holds** (spec 009), and when it was read. Used for 24 hours, then read again (a copy without targets or `regionTargets`, from before spec 006 / 008, or whose `months` are missing or don't hold last month and this month, from before spec 009, is read again at once); **Sales Diary → Refresh salesmen & targets**, Check setup and the Links window refresh it at once (specs 005, 006). Script Properties can only be seen by the script's owner. A salesman's page receives only his own target for this month (his summary: his own for the summary's month); region and house targets reach only the admin. |
| Script cache | `save:<rep>:<saveId>` | What a save did, for 6 hours, so a repeat after a lost reply isn't saved twice (specs 003–005). The admin's saves use `save:admin:<saveId>` (spec 008). |
